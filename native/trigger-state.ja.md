# 遅延トリガーの参照状態

`tools/debian_trigger_state.py`は[発火先の計算](deb-triggers.ja.md)に続く、未処理・処理中・
待機関係の参照モデルである。PythonのファイルIO、導入済みDB、handler起動器は作らない。
原本DEBの状態機械をAdaの稼働実行器へ接続する前に、保持するべき意味を実行試験する。

状態には呼出し側が束縛したtransaction scopeのdigest、増加するrevision、受信者と未処理名、
発火元が待つ受信者、最大一つの処理中batchを保持する。既存の配送結果をactivateへ渡す。
同じ未処理名は集約するが、処理中batchの名前は凍結し、その途中で同じ名前が再発火したら
別の未処理項目として保持する。noawaitの追加で既存のawait関係を消さない。

startは受信者の未処理名を一つの処理中batchへ移す。実行自体はしない。
attemptのdigestはscope・開始revision・受信者・全処理名へ束縛する。
途中の追加発火ではattemptを変えず、次の処理ではrevisionにより必ず別のattemptになる。
古い処理の応答を次の処理へ適用すると拒否する。

observe_successは**別途検証した成功観測を与えた場合の参照遷移**であり、成功を検証するAPIではない。
受信者に新しい未処理トリガーが残っていれば待機者を保持する。
受信者自身が別のパッケージを待っている場合も、その受信者を待つ関係を保持する。
受信者がトリガー処理・待機の両方から解放された場合に限り、上流の待機解除を伝播する。
循環した待機は空の完了状態に変換しない。各edgeを一度ずつ辿る有界処理を使う。
handler失敗・応答喪失・中断では、成功遷移を呼ばず処理中状態を保持する。

## checkpointの意味

encodeは正規化した未認証の状態バイト列を返す。decodeには別途期待するscopeと内容digestが必要で、
異なる内容・scope・非正規形式・重複・範囲外revision・孤立した待機を拒否する。
処理中のcheckpointを復号しても、handler再実行や完了は発生しない。
上限は16 MiB、未処理65,536組、待機262,144組、処理中65,536名。
大きな状態全体を組み立てる前にも符号化サイズを見積もる。

digest照合は署名認証やrollback防止ではない。稼働側は同じroot・transaction・plan・catalogの
認証済みscopeを構成し、既存CAS/WALが指す正確なcheckpointへ束縛しなければならない。
このモデルの出力には実行許可を与えない。検査用の入力から観測を捏造しても導入許可にはならない。

待機先はトリガー名ではなくパッケージであるという意味は、上流の
[トリガー仕様](https://sources.debian.org/src/dpkg/1.17.25/doc/triggers.txt/)を参照した。
これは古い仕様であり、現行全DEBの受入を意味しない。通常構成完了、失敗状態、remove/purge、
登録interestの寿命、循環発火の診断と修復には、完全なpackage lifecycleの統合が必要である。
実行器による観測の認証、native CAS/WALへの接続、handlerと生成物の検査、実電源断は未完である。
