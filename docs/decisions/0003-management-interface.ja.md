# Nia管理機能の公開コマンドと緊急修正

2026-09-08。利用者の最新指示に基づく製品判断。
[単一のパッケージ管理主体](0002-native-package-authority.ja.md)を維持する。

## 所有する機能と公開範囲

Niaが所有する管理操作は、採用した管理コマンド体系だけを利用者向けに公開する。
`nia`、`niactl`、`missionctl`等を代替の公開コマンドとして残さない。
内部API、SDK、署名器、workerは実装上の接続点であり、別の管理主体や公開操作体系ではない。
`smit`・`smitty`の画面も同じ操作要求、認可、結果、監査を使う。

systemd等の独立した外部ソフトウェアは、その正規コマンドを維持する。
`systemctl`の別名として`startsrc`等を作る実装は採用しない。
ネットワーク、デバイス、アカウント、ストレージの既存工具にも同じ境界を適用する。
Niaのトランザクションが必要とする外部観測や副作用adapterと、
外部ソフトウェアの利用者向けコマンドを置き換えることは別である。

自作ソース、ファイル名、識別子、説明はNiaの中立的な名称を使う。
第三者製品との互換性や認定を製品名で表示しない。
原本パッケージのメタデータ、ライセンス、過去のhashに束縛された証跡は改変しない。

## 公開する操作

| コマンド | Niaで所有する役割 |
| --- | --- |
| `installp` | 適用、確定、未確定更新の取り消し、削除、事前検査、復旧 |
| `geninstall` | 対応する供給形式から同一管理器へ要求を渡す入口 |
| `install_all_updates` | 導入済み集合を供給元の更新へ進める |
| `instfix` | 修正IDから対象集合を照合し、導入・適用状況を管理する |
| `lslpp` | 導入版、状態、履歴、所有ファイルと依存関係を表示する |
| `lppchk` | 所有物の内容・サイズ・リンクと導入集合の整合性を検査する |
| `suma` | 更新の取得、取得タスクとスケジュールの管理 |
| `inutoc`・`lppmgr` | 配布索引の構築とメディアの参照を考慮した管理 |
| `emgr` | 暫定・緊急修正の適用、一覧、検査、削除とパッケージ保留 |
| `epkg` | 暫定・緊急修正成果物の作成 |
| `smit`・`smitty` | Niaの対話管理。`update_all`等のfast pathも同じ操作へ接続 |

これは実装済み一覧ではない。[状態台帳](../../native/management-commands.json)と
[現在の実装範囲](../../native/commands.ja.md)で未接続部分を明示する。
名称だけを付けた常時成功コマンドは提供しない。

## 応答インターフェースの適合

利用者が要求する同等性は、コマンド名・引数だけでなく操作時の挙動と応答も含む。
各採用コマンド・オプションについて、次の項目を参照仕様と照合して受入する。

- 表示する項目名、列の順序、整列、並び順、見出し、状態名、処理段階と結果要約。
- 標準出力と標準エラーの使い分け、終了コード、quiet/verbose時の出力。
- 確認プロンプトの文言・既定選択・入力規則、非対話入力・EOF・取消・割込み時の挙動。
- コロン区切り等の機械処理用形式、見出し抑止、空集合と部分失敗の表現。
- 対話画面のfast path、入力フォーム、キー操作、コマンド表示、ヘルプと結果画面。
- 適用・確定・取り消し・削除・保留・中断・復旧の状態遷移と、それに対応する応答。

各項目は、入力・初期状態・期待出力bytes・期待終了値・期待する副作用を持つ
固定fixtureで検査する。時刻等の変動値は事前に定義した項目だけを正規化する。
TTYと非TTY、パイプ、locale、長い名前、空集合、複数対象の一部失敗も対象とする。
ヘルプや引数解析の成功を、操作や応答の適合成功に代用しない。

表示するパッケージ名、版、アーキテクチャ、所有物、修正状態はNiaの実データを使う。
異なるプラットフォームの値・修正ID・認定を生成しない。
Debianのepochを含む版など、既定の区切り文字と衝突する実データの表現も
項目ごとの適合設計に含め、機械処理で列がずれる出力を出さない。
Niaの内部JSON・SDKの診断文を、そのまま利用者向け応答として露出しない。

応答fixtureと実行器の接続は未実装。現段階で全面的な応答互換性を宣言しない。

## 適用・確定・取り消し

`installp -a`の適用完了時点でも、更新前の復旧対象を保持する。
`-c`は受入条件を満たした更新を確定し、復旧対象の保持条件を変更する。
`-r`は未確定更新を取り消す。`-u`はパッケージ自体の削除である。
初回導入と更新の区別、依存する変更のまとめ方、再起動待ちの表示も実装する。

既存の`Pkg_Acceptance`は試行・検証・受入・確定を分けている。
ファイル実行器のWALを確定することと、利用者が復旧可能期間を終了することを
一つの操作へ潰さない。復旧世代は他の参照・保留が残る限り削除しない。

## 緊急修正の構造

通常DEBのアップロード緊急度と、独立して管理する暫定修正成果物を分ける。
前者の`emergency`指定だけで後者を生成したり、検査を省略したりしない。

`epkg`は非特権の成果物作成器にする。初期方式は、元のDEB形式を維持した
完全な置換パッケージを、対象ベースと修正契約に結び付ける方式とする。
署名対象には修正ID、対象release/architecture、正確なベース版とdigest、
置換成果物・対応ソース・効果契約のdigest、依存修正、競合、置換関係、
有効化条件、復旧条件、発行・失効世代を含める。成果物作成と発行認可は分離する。
任意のhost scriptや一時的なファイル上書きを修正成果物として認めない。
[native v1形式](../../native/interim-package.ja.md)の作成器・読取器と、
epkgのテンプレート作成・emgrの内容表示を実装した。署名検証器と稼働操作は未接続である。

`emgr`は通常パッケージと同じcatalog、writer予約、CAS/WAL、設定・効果検査を使う。
別の導入DBは作らない。catalogはベース、現在有効な修正、実際の有効版と所有権を
同時に表現し、修正適用中のパッケージは`lslpp`でも識別できるようにする。
保留は`emgr`だけでなく、`installp`、一括更新、対話画面、自動処理にも適用する。

通常更新が修正を包含する場合、明示された置換関係と元形式の再検査を条件に、
更新・修正解除・保留解除を一つの復旧可能なトランザクションで行う。
単に版番号が新しいことや、ファイルが同じことだけで修正を包含すると判断しない。
修正の除去は有効版・所有権・設定と保留状態を一緒に復旧し、業務データや失効世代を
巻き戻さない。修正同士の依存・競合と途中停止を検査する。

`Pkg_Advisory`、`Pkg_Exposure_Policy`、`Pkg_Holds`、`Pkg_Acceptance`を接続・拡張する。
SDKの容量境界や公開形式の変更には移行・試験を伴わせる。
メモリ上のカーネル更新は、対応する実機構と署名・復旧契約が受入されるまで公開しない。

## 配布への切替条件

現行ISO 09と既存componentの配布記録には旧`/usr/bin/nia`がある。
これを新方針への適合済みとは扱わない。現在のCLI試作を旧ISOへ入れ替えて完成にしない。
新規nativeイメージでは公開コマンド集合とPATH、代替入口の不在、単一writer、
通常更新と修正の相互作用、保留、再起動、途中停止・容量不足・失効時の復旧を受入する。
